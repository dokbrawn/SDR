# Исходники

## `main.c` → исполняемый файл `pluto_link`

Полнодуплексный приём/передача между двумя ADALM-Pluto через SoapySDR (драйвер `plutosdr`,
формат отсчётов CS16). Одна программа, режим задаётся аргументом командной строки.

```
pluto_link <tx|rx> <uri>

  tx|rx   режим платы (определяет, на какой частоте передаём и на какой слушаем)
  uri     адрес устройства из вывода `SoapySDRUtil --find` (usb:3.4.5, ip:192.168.2.1)
```

### Режимы, частоты и TX-файл

Режим `tx` передаёт не сигнал из кода, а CS16-файл (третий аргумент, по умолчанию
`tx_name.pcm`): кадр генерирует `scripts/gen_tx_name.py`
(текст → биты → Gray-QPSK → upsampling ×4 → прямоугольный импульс; кадр =
тишина 2048 + преамбула 16 символов + данные). Буфер потока заполняется файлом по кругу,
без пауз: паузы существуют только внутри кадра. В версии урока 8 запись в поток шла
через буфер (`count % 2 == 0`) — поток голодал, кадр резался на всплески; убрано 02.11.

```
./build/pluto_link tx usb:3.4.5 my_frame.pcm
```

### Режимы и частоты

| Режим | TX | RX | Файл записи |
|---|---|---|---|
| `tx` | 800 МГц | 840 МГц | `rx_from_840.pcm` |
| `rx` | 840 МГц | 800 МГц | `rx_from_800.pcm` |

Плата `tx` передаёт на 800 МГц, её слушает плата `rx`; та одновременно передаёт на 840 МГц,
и этот сигнал пишет себе плата `tx`. То есть обе платы работают одновременно и на приём, и на передачу.

### Параметры (захардкожены в `main.c`, строки с `const`)

| Параметр | Значение | Где в коде |
|---|---|---|
| Sample rate (TX и RX) | 1 МГц | `sample_rate` |
| Bandwidth (TX и RX) | 200 кГц | `bandwidth` |
| TX gain | 71 дБ | `gain_tx` |
| RX gain | 60 дБ | `gain_rx` |
| Передаваемый сигнал | тон 10 кГц, амплитуда 32000: `I = A·sin(2πft)`, `Q = A·cos(2πft)` | `tone_hz`, `amp` |
| Формат потока | CS16 (int16 I, int16 Q) | `setupStream` |
| Размер буфера | MTU потока (TX 4096, RX 32768 отсчётов) | `getStreamMTU` |
| Таймаут `readStream` | 1 000 000 мкс | `timeoutUs` |
| Вывод RMS | каждые 100 буферов | `count % 100` |

> **Внимание:** в отчёте по занятию 6 описана более ранняя версия, где передавалась константа
> `I = Q = 8000` (прямоугольный импульс). Сейчас в коде — тон 10 кГц. Обе версии надо описать
> в отчёте раздельно, иначе текст противоречит коду.

### Что делает программа по шагам

1. Разбор аргументов, проверка режима и URI.
2. `SoapySDRDevice_make` с аргументами `driver=plutosdr`, `uri`, `loopback=0`.
3. Настройка TX: sample rate, частота, bandwidth, gain → `setupStream(CS16)` → MTU.
4. То же для RX.
5. Выделение буферов, заполнение TX-буфера сигналом (один период длиной в MTU).
6. `activateStream` для TX и RX, установка обработчика SIGINT/SIGTERM.
7. Открытие `.pcm` на запись.
8. Цикл: `readStream` → RMS + `fwrite` → `writeStream`.
9. По Ctrl+C: `fclose`, `deactivateStream`, `closeStream`, `unmake`, `free`.

### Сборка

```bash
cmake -S .. -B ../build && cmake --build ../build -j"$(nproc)"
# или без CMake:
gcc main.c -o pluto_link $(pkg-config --cflags --libs SoapySDR) -lm
```

Полная инструкция с установкой зависимостей — [../BUILD.md](../BUILD.md).

### Известные недостатки (что чинить следующим)

| Проблема | Где | Как чинить |
|---|---|---|
| Ошибки `writeStream` проглатываются пустым `if` | основной цикл | считать и печатать переполнения/таймауты, логировать потери |
| Все параметры захардкожены | `const` в начале `main` | вынести в аргументы CLI (`getopt`): частота, gain, Fs, имя файла |
| Возврат `readStream` трактуется как `int sr`, хотя API возвращает `int` числа элементов — при отрицательном коде ветка просто пропускается без диагностики | основной цикл | печатать код ошибки (`SOAPY_SDR_TIMEOUT`, `OVERFLOW`) |
| Нет проверки `setSampleRate`/`setFrequency` на ошибку | настройка | проверять код возврата и печатать `SoapySDRDevice_lastError()` |
| Один файл на весь функционал | `main.c` | вынести инициализацию устройства/потоков в `pluto_sdr.c/.h` (как в учебном проекте курса) |
| Нет тестов | — | хотя бы `loopback`-режим на одном устройстве как smoke-test |
